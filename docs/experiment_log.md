## Problems and fixes
- **2026-09-19 — Bug 1: augmentation corrupted training images, cnn_v1 converged to ~24% (majority-class prediction).** `RandomBrightness`/`RandomContrast` default to `value_range=(0, 255)`, but `src/data.py` applied augmentation *after* per-model rescaling (custom_cnn's images were already in `[0, 1]`; vgg16's were already mean-subtracted by `preprocess_input`). A "brightness shift" sized for a 0-255 range added to a 0-1 image pushed pixels to ~13-51 (several images collapsed to all-zero), destroying the signal — confirmed by inspecting a batch directly. Fixed by moving augmentation to run on the raw `[0, 255]` grayscale images, before preprocessing, for both models. Verified: post-fix batch stats are back to sane ranges (`[0, 1]` for custom_cnn, ~`[-124, 151]` for vgg16, matching `preprocess_input`'s expected range).

- **2026-09-19 — Bug 2: "balanced" class weights (disgust ≈9.5x) destabilized training even after fixing Bug 1.** A controlled CPU test (same seed/data, 15% subset, 8 epochs) showed training climbing normally with `class_weight=None` but stuck at ~14% (chance level) with sklearn's `"balanced"` weights — lowering the learning rate to 3e-4 didn't fix it either. Root cause: a single "disgust" example appearing in a batch got ~9.5x the gradient weight of an average example, producing large, noisy updates given how rare it is per-batch even at full dataset scale. Fixed by adding `config.CLASS_WEIGHT_MODE` ("sqrt", default) and `CLASS_WEIGHT_MAX` (3.0): `src/data.py` now supports `"none"`/`"balanced"`/`"sqrt"`, with `"sqrt"` square-rooting the balanced weights and capping them (disgust: 9.5x → 3.0x). Verified via the same controlled test: sqrt-damped weights at the config's default lr=1e-3 climbed just like the no-weight run. Also added `val_macro_f1` (sklearn) to `src/train.py`'s per-run logging (`results/runs.csv`), since accuracy alone can hide a collapse onto majority classes.

- Both bugs confirmed independent of the model/labels: `src/debug_data.py` showed clean `[0,1]` pixel stats and correct label-to-face matches; `src/debug_overfit.py` showed the model reaching 100% accuracy memorizing a single fixed batch (dropout=0/l2=0 by step 25; real config by step 50) — the architecture and data pipeline were never the problem.

- **2026-09-21 — `vgg16_v1_history.csv` from Kaggle held three runs, not one.** It had 120 rows: three 40-epoch runs stacked (epoch counter resets at rows 0, 40 and 80). `train.py` opens its `CSVLogger` with `append=True` (needed so VGG16's two stages share one file), and the Kaggle sessions reused the run name `vgg16_v1`, so each attempt appended to the earlier file. Only the last block belongs to the saved model: its best val_acc (0.6600092649...) matches the `runs.csv` row exactly, and it has 40 epochs. The earlier blocks (best 0.6670 and 0.6540) are stale runs whose checkpoints were overwritten, so the 0.6670 must not be quoted as a result. `results/vgg16_v1_history.csv` was trimmed to that last block; the raw 120-row file is still in `~/Downloads/vgg16_v1_results/out/`. The curves PNG is drawn from the in-memory history, so it was already clean (one run, boundary at epoch 15). Not yet fixed in code: `train.py` should remove an existing `{run_name}_history.csv` before a fresh run starts. A leftover `vgg16_smoke` row (2 epochs, 96px) was also removed from `results/runs.csv`; it came along in the Kaggle copy of that file.

- **2026-09-21 — Phase 5 `src/robustness.py` had two bugs, both hidden until it met real trained models.** (1) *Out of memory:* it preprocessed all 7,178 images for VGG16 into one array (7,178 x 224x224x3 float32 = 4.3 GB, plus copies) and the kernel OOM-killed the process at ~11.7 GB, ~90 s into what was meant to be a ~2 hour run; nothing was written. Fixed by preprocessing and predicting 256 images at a time; peak memory is now ~3.5 GB. (2) *Wrong resize for VGG16:* it upsampled 48->224 with `cv2.INTER_AREA` (nearest-neighbour-like when enlarging), while training uses bilinear `tf.image.resize`. That blocky input dropped `vgg16_v1` from 0.66 to **0.18** accuracy on *clean* faces (checked on 360 images: INTER_AREA 0.181, INTER_LINEAR 0.642, exact training path 0.656 = matches the real evaluation), so every VGG16 robustness number would have been wrong. Fixed by using `tf.image.resize` (bilinear) plus the shared `src/preprocess.py`, i.e. the training preprocessing. `custom_cnn` results were identical before and after (its 48px input is never resized), so its path was never affected. Neither bug showed in the earlier Phase 5 smoke test because that used untrained throwaway checkpoints and only a 5% subset. `src/gradcam.py` imports `_preprocess_for_model` so it gets the resize fix, but its own `_predict_all` still preprocesses the whole set at once and would hit the same OOM at full size; to be fixed when Phase 6 starts. Also worth knowing for Phase 7: `src/realtime.py` resizes face crops with `cv2.INTER_AREA` too, but downscaling real crops is a different situation from upscaling 48px training images.

- `cnn_v1`'s buggy Colab artifacts (model/history/curves) renamed to `cnn_v0_buggy` rather than deleted, for reference. `cnn_v1` must be retrained on Colab with both fixes in place; `vgg16_v1` had not been trained yet, so it never hit either bug.
